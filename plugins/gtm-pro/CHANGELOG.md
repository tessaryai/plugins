# gtm-pro plugin (Tessary GTM Pro) changelog

> **TL;DR (v0.3.0, current: the full plugin of v0.2.1 is now Tessary GTM Pro, `gtm-pro`. Slash commands are `/gtm-pro:<skill>` and the install command is `/plugin install gtm-pro@tessary`. The scripts work as before; a few shared instructions are fixed.)**
> Rename: the full edition moved from `plugins/gtm` to `plugins/gtm-pro`, with name `gtm-pro` and display name "Tessary GTM Pro". It keeps every helper script in `lib/`, the Notion token path, large imports, the API-key adapters and the scripted funnel. Every command is now `/gtm-pro:<skill>`, for example `/gtm-pro:sweep`; releases before v0.3.0 used `/gtm:`, and the command names in the older entries below were renamed. Two editions: `gtm@tessary` (Tessary GTM) is now the directory edition, generated from this plugin by `scripts/build-gtm-edition.py` without `lib/`, for the Anthropic plugin directory. It runs through connectors only and points to this edition at its limits. Switch from `gtm@tessary` 0.2.1: the next marketplace update of `gtm` installs the directory edition, which has no scripts. To keep the full plugin, run `/plugin marketplace add tessaryai/plugins`, then `/plugin install gtm-pro@tessary`, remove `gtm` in the `/plugin` menu so each skill runs only once, and run `/gtm-pro:setup schedules` so the scheduled tasks call `/gtm-pro:` commands. Both editions read the same config folder and format (`config.json`, `state.json`, `logs.md`, `voice.md`, `icp.md`, `credentials.json`), so settings, cursors, logs and saved keys carry over. Shared instruction fixes from an end-to-end test of the directory edition: the funnel definitions now say that with no dated counted contact the tables have one row, the current month, with zeros, and that the deal part of the Missing property check runs only when the deals export has rows (both as `lib/funnel.py` already does); the fetch view un-escape list now includes `:`, and import Existing keys says to split Notes on `<br />` and un-escape before taking a `Source ID:` value, so a second import of the same file matches on Source ID; the import state `folder` is relative to the active config folder. Verified: `claude plugin validate`, the `csv_import.py` and `funnel.py` self-tests. If you pin the marketplace `ref`, use `gtm-pro-v0.3.0`.

> **TL;DR (v0.2.1: directory review fixes. The plugin's behavior does not change.)**
> Fixes from the Anthropic directory's automated checks. The icon is re-encoded at 512 px with no text or EXIF chunks, because the screener read a large share of the old file as printable text. Example links in `lib/funnel.py` and `reference/config.md` no longer spell a Notion host, which the screener read as a place a credential could be sent. `plugin.json` gets `displayName` "Tessary GTM", so the listing reads as Tessary's. The README Privacy section gains a Credentials table: keys are optional, saved by the user in a terminal, kept in `credentials.json` (mode 600), and each goes only to its own vendor's API, enforced by the host allowlist in `lib/readonly_api.py`; Cowork mode reads no keys. Verified: `claude plugin validate` and the lib self-tests. If you pin the marketplace `ref`, use `gtm-v0.2.1`.

> **TL;DR (v0.2.0: gtm now runs in Claude Cowork as well as Claude Code. Settings can live in a `.gtm/` folder in the project, a new `runtime` = `cowork` uses connectors only, setup detects Cowork and guides the user, and most skills run without Python. Tested in a simulated Cowork run in Claude Code, not yet inside the Cowork app.)**
> Config discovery: `lib/config.py` now finds the active config folder as the first of `$GTM_CONFIG_DIR`, a `.gtm/` folder holding `config.json` in the current folder or a parent, and `~/.config/gtm/`. `config.py init --project` creates `.gtm/` with a `.gitignore` that keeps `credentials.json` out of git, and `config.py paths` prints the active folder, its source and why. In Cowork, keep settings in the connected project folder, because files outside it may not last between sessions. Runtime: the new key `runtime` (`claude-code` by default, or `cowork`). With `cowork`, gtm uses connectors only: `set-secret` refuses, `has-secret` prints "not set (runtime is cowork: connectors only, no keys are used)", `lib/notion_rest.py` and `lib/readonly_api.py` refuse to run, `notion.access` stays `mcp`, and an adapter that needs an API key and has no connector is blocked with the fix "connect a connector for <tool>, or run this routine from Claude Code". Every API-key preflight and key fix in the adapters has a Cowork alternative (a connector, or a CSV export for imports). `config.py check` warns that the tools listed under API-key adapters must use a connector, because `check` cannot see connectors. Bulk reads of a large CRM (big imports, large campaign and sweep batches) point the user to Claude Code with a token, run against the same project folder. Setup: a new step 0 asks where gtm runs, with a best-effort probe (`~/.claude` present, whether `api.notion.com` can be reached, `python3` present) that sends no data and is the only allowed direct call to the Notion API host in Cowork; the user's answer wins over the probe. It then asks where to keep settings, explains in plain words what works in Cowork, and runs `paths` and `show` from the project folder. Schedules: in Cowork, setup schedules only when a scheduled-tasks tool is present; otherwise it tells the user to run the skills on demand or schedule them from Claude Code on the same computer, pointed at the same folder. No Python: `reference/config.md` (No Python) gives the rules for writing and checking config by hand, including a manual time zone check; most skills run with smaller limits, and the funnel report and imports of more than 200 rows need Python. New config key `sweep.exclude_labels` (default `[]`): Gmail labels, such as a warm-up or sequencer label, whose mail the sweep skips; setup asks for it, and the Gmail adapter now allows the read-only `list_labels` tool, only to map label ids to names. Other fixes that also apply in Claude Code: the Gmail sent query reads ids only (`THREAD_VIEW_IDS_ONLY`, page size 50, to the end) and opens only threads the main query did not return; a first LinkedIn read with an empty CRM opens no threads and visits no profiles, and with contacts opens at most 20 matching threads; the connections list is checked before any profile visit; meetings with no matched contact are listed under Unmatched instead of being dropped; the Fathom adapter pages with the connector's `cursor` and `next_cursor`; a campaign-run dry run outside the send window or on a non-working day still prints the exact text, marked as such; `funnel.py normalize` with no rows prints a plain "0 rows (empty)" line. The plugin README has a new "Use gtm in Cowork" section and a Privacy section (no telemetry, nothing sent to Tessary, where settings and keys are stored). Verified: a simulated Cowork run in Claude Code (setup, sweep, a campaign-run dry run and funnel) with settings in a project `.gtm/` folder and `runtime` = `cowork`, and nothing written to `~/.config/gtm`; `config.py` in a scratch project folder (`init --project`, `paths`, `check`, `exclude_labels` validation, secret refusal in Cowork); the refusal of `notion_rest.py` and `readonly_api.py` in Cowork; `funnel.py self-test`, `csv_import.py` self-test and `py_compile` of every `lib/` file. Not verified: any run inside the real Cowork app, including the step 0 probe in a Cowork VM; whether scheduled tasks work in Cowork; whether files outside the connected folder persist in Cowork; any real send (still untested, as in v0.1.0); the fixed skills against live connectors after the last round of fixes. If you pin the marketplace `ref`, use `gtm-v0.2.0`.

> **TL;DR (v0.1.0 — initial release: a Notion-hosted CRM and seven go-to-market skills, `/gtm-pro:setup`, `/gtm-pro:import`, `/gtm-pro:sweep`, `/gtm-pro:campaign-build`, `/gtm-pro:campaign-write`, `/gtm-pro:campaign-run` and `/gtm-pro:funnel`. Tested end to end against a live Notion workspace and real connectors; no live send yet.)**
> `/gtm-pro:setup` creates five Notion databases (Contacts, Companies, Pipeline, Campaigns, Meetings) and a Funnel page from `templates/schema.json`, or maps an existing set through `notion.field_map`, `notion.status_map` and `notion.option_map`, and writes `~/.config/gtm/config.json`. Every skill works with only the Notion connector; a Notion integration token, when saved, moves bulk work to `lib/notion_rest.py`. `/gtm-pro:import` reads a CSV or Google Sheets export, HubSpot, Pipedrive or Attio read-only, dedupes by email, LinkedIn URL and company domain, and writes only after a preview and a yes. `/gtm-pro:sweep` mirrors email, calendar, LinkedIn (Claude in Chrome), meeting recorders and outreach tools into the CRM with forward-only Status changes and dated log lines. `/gtm-pro:campaign-build` sources and scores an audience from the ICP with the enrichment adapters; `/gtm-pro:campaign-write` writes the sequence and per-contact copy in the user's voice and leaves the campaign at Review; `/gtm-pro:campaign-run` sends only for Active campaigns, only text found word for word on the pages, with every gate (Do Not Contact, reply stop, working days and send window, daily caps, verify before marker). It defaults to live mode, with a LinkedIn invite cap of 10 a day and a plain account-risk warning in setup; `sending.mode` = `dry-run` or a `dry-run` argument sends nothing. `/gtm-pro:funnel` counts with `lib/funnel.py` and publishes only when its checks pass. Adapters in v1: email (gmail, outlook), calendar (google, outlook), linkedin (chrome), meetings (fathom, granola, fireflies, otter), outreach (gojiberry, lemlist, instantly, apollo), enrichment (exa, apollo, hunter, mcp), notify (push, slack), import (csv, hubspot, pipedrive, attio). Secrets live only in `~/.config/gtm/credentials.json` (`chmod 600`), saved with `config.py set-secret` at a hidden prompt; the API client `lib/readonly_api.py` is GET-only with a fixed path allowlist. Verified: `--help` of every `lib/` script on the default `python3` and on Python 3.9, the `funnel.py self-test`, and scratch smoke tests of `notion_rest.py` (bad id and fake token give clean exit codes and never print the token), `readonly_api.py` (missing key, path off the allowlist), `csv_import.py suggest` and `plan`, and `config.py` (`set`, `get`, `state-set`, secret refusal, masking in `show`). End-to-end test (MCP only, no token): setup created the five databases (50 properties, 5 two-way relations) and the Funnel page under a test page; import ran twice from a CSV with no duplicates; campaign-build and campaign-write built a 4-contact campaign with an enrichment MCP and Exa; sweep read real Gmail, Google Calendar, LinkedIn (Chrome), Fathom and Gojiberry and wrote only to the test CRM; campaign-run planned the day in dry-run mode (3 LinkedIn invites, external campaigns skipped); funnel published to the test Funnel page. About 70 defects found in those runs are fixed, among them: the Notion connector's rows and SQL queries share a small workspace quota (skills now read in view mode through `notion.views`), relation filters with a bare page id are silently ignored (skills now compare page ids), lines written without a blank line merge into one paragraph, and the fetch view escapes `_ { }`. Not verified: any real send, the REST path against the test CRM, the Outlook, Granola, Fireflies, Otter, lemlist, Instantly, Apollo, Hunter, HubSpot, Pipedrive and Attio adapters, and the vendor field names, paging and UI paths in the HubSpot, Pipedrive, Attio, lemlist, Instantly, Apollo, Hunter, Fireflies, Granola, Otter, Fathom and Outlook adapters; each adapter tells the agent that the live schema wins. Known limits: LinkedIn people search is not in v1; Apollo (outreach and enrichment) needs the Apollo connector; Attio import without its connector goes through a CSV export. If you pin the marketplace `ref`, use `gtm-v0.1.0`.
